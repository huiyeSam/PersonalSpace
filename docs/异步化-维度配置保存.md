# 异步化：维度配置文件保存

> 引入版本：1.0.64-mc1.12.2
> 涉及文件：`world/AsyncDimensionSaver.java`（新增）、`world/DimensionConfig.java`、`PersonalSpaceMod.java`

## 要解决的问题

维度配置保存走 `DimensionConfig.syncWithFile(file, write=true, dimId)`，内部使用 Forge 的
`Configuration`：每次保存都会**重新解析整个文件再整体重写**，即"读 + 写"两次磁盘 IO。

触发点全部在服务端主线程：

- `WorldEvent.Save`（世界自动保存，每个脏维度都写一次）
- `WorldEvent.Unload`（维度卸载）
- `FMLServerStoppingEvent`（关服时保存全部）
- `PortalTileEntity.updateSettings`（玩家改设置、创建维度）

个人维度多的服务器上，自动保存会造成可感知的 tick 卡顿。

## 实现方案

### 总体思路：主线程快照 + 单后台线程有序写入

```
主线程 (saveDimensionConfig)
  ├─ 同步部分：解析存档根目录、mkdirs（保持原有 IOException 语义）
  ├─ config.createSaveSnapshot()        ← 复制出一份快照
  ├─ config.clearNeedsSavingForAsyncSave() ← 清脏标记，防止同一保存被重复排队
  └─ AsyncDimensionSaver.saveAsync(...) ← 提交后立刻返回
后台线程 (PersonalSpace-DimensionSaver, daemon)
  └─ snapshot.syncWithFile(file, true, dimId)  ← 真正的磁盘 IO
```

### 为什么用单线程线程池

- 同一文件的多次写入需要**严格有序**（后提交的保存必须覆盖先提交的），单线程执行器
  天然保证提交顺序 = 执行顺序。
- 不同维度的文件之间不需要并行（文件很小，瓶颈是主线程被阻塞，不是吞吐量）。
- daemon 线程，不会阻止 JVM 退出。

### 快照（DimensionConfig.createSaveSnapshot）

复制 `syncWithFile` 写入路径会读到的**全部字段**：视觉、世界生成、边界、间隔/马路、
中心标记、时间天气、传送点、存档目录名。

- `layers` 用 `new ArrayList<>(layers)` 做结构复制；`FlatLayerInfo` 元素在本 mod 中
  从不被原地修改（只整体替换列表），所以浅拷贝元素是安全的。
- 快照直接写字段（同类内可访问私有字段），不经过 setter，避免触发 `needsSaving` 副作用。
- 提交后快照被视为不可变：后台线程只读它。

### 脏标记的竞态处理

- 提交保存**时**就清除 live config 的 `needsSaving`，否则下一个自动保存事件会把同样的
  内容再排一次队。
- 清除之后任何 setter 被调用都会重新置脏 → 写入在飞行途中发生的新修改会被**下一次**
  保存事件捕获，不会丢。
- 后台写入失败时：`LOG.error` + 把 live config 重新 `markDirty()`，下次保存事件重试。

### 关服与重启

- `FMLServerStoppingEvent`：先把所有脏配置照常提交（此时已是异步），然后调用
  `AsyncDimensionSaver.flushAndWait()`：关闭执行器并 `awaitTermination(30s)`，
  保证关服前所有排队写入真正落盘。
- `flushAndWait` 之后 `shutDown=true`，此后 `saveAsync` 退化为同步写（兜底，
  理论上不会走到，因为 `worldUnload` 已被 `stopping` 标志拦住）。
- `FMLServerAboutToStartEvent` 调 `AsyncDimensionSaver.reset()` 复位标志——
  单机下"退出到主菜单再进存档"JVM 不退出，必须能重新开始异步保存。

### 创建新维度的顺序

`updateSettings` 中先 `saveDimensionConfig`（现在只是排队），再
`registerWithDimensionManager` + `initDimension`。注册和初始化**不读文件**
（配置对象已在内存中），所以文件稍后落盘不影响创建流程。

## 已知取舍

- 极端情况（写入排队后 JVM 直接崩溃）会丢这一次配置写入；配置只是维度设置，
  区块数据由 MC 自己的区块保存负责，不受影响。关服路径有 flush，正常退出不会丢。
